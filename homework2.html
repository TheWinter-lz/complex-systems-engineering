线控底盘平台需求规格分析

复杂系统工程 · 小组作业2 · BRS 与 StRS · ConOps / OpsCon / 相关方需求

0 · 作业概述

系统对象与作业目的

所选系统：面向高级别自动驾驶（L4/L5）的线控底盘平台（延续作业1所确定的 System 层级对象）。该平台向上对接自动驾驶决策规划系统，向下驱动转向、制动、驱动等执行子系统，是车辆运动控制的执行核心。

作业目的：围绕所选系统，结合小组讨论与 AI 问答，完成业务/任务分析与相关方需求分析及定义；参考《第4章 概念定义》表 4-1（BRS 范例轮廓）与表 4-5（StRS 范例轮廓），完整输出业务需求规格说明书（BRS）与相关方需求规格说明书（StRS）。

BRS（业务需求规格说明书）

在组织/业务层面描述业务环境、目的目标、业务模型与业务运行需求，回答"为什么做、业务上要实现什么、用什么指标衡量成功"。

StRS（相关方需求规格说明书）

从用户、操作者、维护者等相关方视角，在使用环境中派生准确、清晰、可验证的系统需求，回答"各方需要系统做到什么"。

1 · BRS 业务需求规格说明书

业务需求规格说明（Business Requirements Specification）

1. 简介

1.1 业务目的：推动高级别自动驾驶商业化落地，需要底盘由"由人操控的机械总成"转变为"可被自动驾驶系统直接调用、可闭环验证的执行平台"。本项目旨在构建标准化、平台化的线控底盘执行底座，支撑多车型自动驾驶产品的研发、适配与量产交付。

1.2 业务范围：业务域为智能电动汽车底盘执行系统；业务活动范围覆盖平台需求分解、开发验证、量产装配、交付运营与售后迭代；系统范围包括线控转向、线控制动、线控驱动、底盘集成控制及其控制软硬件，不含上层感知、决策与规划算法。范围外实体包括自动驾驶域控制器、整车车身与座舱、路侧与云控平台。

1.3 业务概况：内部由转向、制动、驱动、集成控制与底盘域控等分块构成；外部对接自动驾驶域控制器、整车厂、出行运营方、监管认证机构与乘员，各实体通过标准机械、电气与通信接口相互关联。

1.4 定义：线控底盘（X-by-Wire Chassis）：以电信号替代机械/液压连接完成转向、制动、驱动力矩传递的底盘系统；功能安全按 ISO 26262 评估，预期功能安全参考 ISO 21448（SOTIF）。

1.5 主要相关方：整车厂（OEM）、自动驾驶方案商、整车集成与测试团队、零部件供应商、出行/运营服务商、监管与认证机构、乘员/最终用户、运维售后团队。

2. 业务管理需求

2.1 业务环境

  • 政策法规：智能网联汽车准入与上路管理、功能安全/预期功能安全与信息安全合规要求；
  • 市场趋势：Robotaxi、无人配送、干线物流等自动驾驶场景走向商业化；
  • 技术基础：线控执行器、分布式电驱动、车用总线（CAN/LIN/Ethernet）与冗余通信日趋成熟；
  • 社会责任：保障道路交通安全、降低能耗与排放。

2.2 使命、目的与目标

  • 使命：为 L4/L5 级自动驾驶提供安全、可靠的车辆运动执行底座；
  • 目的：使自动驾驶决策规划指令能够被高精度、高可靠地转化为车辆横纵向运动；
  • 目标：达到规定的响应时延、控制精度、冗余可用率与乘坐舒适性指标。

2.3 业务模型

  • 以平台化产品供给整车厂与出行运营商，支撑多车型适配与批量交付；
  • 通过后续 OTA 迭代、诊断数据回传与售后运维形成持续服务；
  • 以标准化接口降低跨车型、跨供应链的集成成本。

2.4 信息环境

  • 项目组合：多车型底盘平台共线开发，明确项目间优先级与定位；
  • 长期系统计划：与整车电子电气架构演进路线保持一致；
  • 数据配置：统一的车辆运行数据、故障诊断库及其可用性、可访问性约束。

3. 业务运行需求

3.1 业务过程：订单与需求输入 → 平台需求分解 → 子系统/模块开发 → 台架/在环/整车验证 → 量产装配 → 交付运营 → 运维与迭代，各过程之间以接口与数据交付物衔接。

3.2 业务运营策略与规则：

  • 每条底盘控制指令必须闭环校验，执行结果需反馈回上层系统；
  • 检测到故障时须按规则降级运行并上报，必要时进入最小风险状态；
  • 关键控制过程与故障事件须留痕记录，支持事后追溯与审计。

3.3 业务运行约束：满足功能安全 ASIL-D 相关约束；控制响应时延 ≤ 10 ms；适应车用温度、振动与电磁环境；满足车载信息安全（防篡改、防劫持）要求；在既定成本与进度范围内交付。

3.4 业务运行质量：高层级可用性目标 ≥ 99.999%；兼顾效能、效率与乘坐满意度；紧急安全工况的优先级高于一般舒适性与经济性指标。

3.5 业务结构：设置底盘系统团队、子系统团队、模块团队、测试验证团队与运营支持团队；明确各角色职责，并支持未来平台化扩展带来的结构调整。

4. 提案系统初步运行概念

4.1 初步运行概念：线控底盘平台作为黑盒执行核心，接收自动驾驶规划给出的轨迹/力矩指令，完成横纵向运动控制并反馈状态；支持自动驾驶模式、人工兜底模式与最小风险策略；相关人员包括远程安全员、运营调度人员与维护人员；运行于整车供电、总线通信与诊断工具所构成的支持环境中。

4.2 初步运行场景：以"城市道路巡航跟车—变道—路口通行—泊车"为典型场景串接平台运行过程；另给出执行器降级、通信中断等退化与异常场景（详见第 6 章 OpsCon）。

2 · StRS 相关方需求规格说明书

相关方需求规格说明（Stakeholder Requirements Specification）

1. 简介

1.1 相关方目的：从使用者、操作者、维护者及监管者等视角，把业务价值落实为可执行、可验证的系统需求，确保各方需要与期望在需求中得到充分反映并达成一致。

1.2 相关方范围：覆盖系统采办、开发、集成、运行、维护与监管全生命周期的相关方，包括可能受系统影响或能够影响系统的个人与组织。

1.3 概况：StRS 衔接 BRS 所定义的业务环境与后续系统需求（SyRS），在特定使用环境中派生使用者、操作者、维护者等相关方的准确需求。

1.4 定义：需要（Need）是相关方立场上的意图与期望，是需求的输入；需求（Requirement）是需要经过完整性、正式表达与多方权衡分析后的结果，须有约束边界、可行且可验证。

1.5 相关方：详见第 3 章相关方列表与分析矩阵。

2. 系统运行需求

2.1 系统过程：指令接收 → 横/纵向控制求解 → 执行器驱动 → 状态反馈闭环；过程中持续进行故障监控；出现异常时触发冗余切换与最小风险策略。

2.2 系统运行策略与规则：双通道/双冗余通道之间按规则切换；失效安全规则保证任意单点故障不导致不可控；人机交接与远程接管规则须明确责任边界。

2.3 系统运行约束：受成本、进度、软硬件接口、通信协议、功能安全与信息安全合规等约束；需求须独立于具体实现设计，保留多种可行实现路径。

5 · ConOps 运营概念（体系 / 组织层面）

Concept of Operations

层级定位：ConOps 在组织/体系层面描述组织预期的运作方式、目的与目标，面向由多个系统组合而成的体系，描述系统之间多对多的交互关系。

目标、目的与期望

  • 在智能网联交通体系中，实现车辆运动执行的安全、高效与舒适；
  • 支撑单车智能与车路云协同下的自动驾驶商业化运营；
  • 形成可复制、可扩展的底盘平台能力。

项目范围与相关方职责

  • 范围：线控底盘平台及其与自动驾驶系统、整车、云控平台的接口；
  • OEM 负责整车集成与量产，方案商提供决策规划；底盘团队开发执行平台，运营方负责车队调度，机构负责合规监管。

系统集如何运行

  • 车辆在 V2X 体系中单车或编队运行，底盘作为执行核心承接上层指令并反馈状态；
  • 云控平台进行远程监控、调度与 OTA，路侧单元提供环境协同信息。

运行与支持环境

  • 运行环境：城市道路、园区、场站等自动驾驶场景；
  • 支持环境：整车供电与通信网络、诊断工具、充电与运维设施、云端数据平台。
6 · OpsCon 运行概念（系统层面）

Operational Concept

层级定位：OpsCon 针对某一特定系统，从用户视角描述系统将做什么、为什么这么做；以目标系统为核心，描述其与体系中其他系统的一对多交互关系。

7.1 上下文环境与外部接口

  • 上游：自动驾驶域控制器（下发轨迹、力矩/转向/制动指令）；
  • 下游：转向、制动、驱动等执行子系统；
  • 支撑：整车 12V/48V 电源、车载总线、诊断与监控接口；
  • 人员：远程安全员、运营调度人员、维护人员。

7.2 正常运行场景

  • 巡航跟车：依据规划轨迹维持车速与车距，纵向驱动力矩/制动力矩闭环控制；
  • 变道通行：协调横向转向与纵向车速，完成平稳变道；
  • 路口通行 / 泊车：低速工况下精确控制转向与制动，保障就位精度。

7.3 退化运行场景

  • 单通道或单个执行器性能下降时，冗余通道接管，维持基本可控运行并提示降级；
  • 部分传感器精度受限时，采用降级控制策略，限制车速与工况。

7.4 异常场景与最小风险策略

  • 执行器卡死、通信中断或关键传感器失效时，触发失效安全规则；
  • 按策略进入最小风险状态：减速、靠边、驻车，并向远程安全员与监控平台上报。
7 · 需求追溯与小结

追溯关系与结论

追溯链路：业务需求（BRS）→ 相关方需求（StRS）→ 后续系统需求（SyRS）→ 子系统与模块需求。每条相关方需求均可追溯到对应相关方及其原始需要，并在验证阶段对应到相应测试或评审活动。

小结：本次作业以"面向高级别自动驾驶的线控底盘平台"为对象，依据表 4-1、表 4-5 框架完成了 BRS 与 StRS 的概念定义：在业务层面明确了目的、环境、模型与运行质量，在相关方层面识别并分析了九类相关方，将其需要转化为八项可验证需求，并区分了体系层面的 ConOps 与系统层面的 OpsCon，为后续系统需求定义与架构设计奠定基础。
